# SIDDHI Nepal — website rebuild brief

## How to use this document

This is an implementation brief, not a suggestion list. Sections marked **LOCKED** are
decisions already made after evaluating alternatives — implement them, don't re-open them.
Sections marked **ASK FIRST** depend on facts nobody has yet; stop and ask rather than
inventing an answer.

Work in the order given in "Build order" at the bottom. Do not start on landing page
animation until the content model and one working detail page exist.

---

## 1. Context

SIDDHI Nepal is a public health research and implementation NGO registered with Nepal's
Social Welfare Council, based in Kathmandu. They run survey research (climate and health,
adolescent mental health), work with Paropakar Maternity Hospital and Kageshwori Manohara
Municipality, and produce SBCC materials.

The current site is `https://www.siddhinepal.org` — a single-page brochure where every
"Details" link is a dead `#`. The copy is decent and should be migrated, not rewritten.

**Who this site is for:** grant program officers, government and municipal partners,
academic collaborators. Not retail donors.

**What the site is for:** establishing research credibility and making their work
citable and findable. It is not a fundraising funnel.

## 3. LOCKED decisions

- **Payload CMS 3 installed into the Next.js app.** One repo, one deploy. Not headless
  SaaS, not WordPress, not a separate backend.
- **Postgres via Neon** (`@payloadcms/db-postgres`), London region. SQLite was the earlier
  pick and was reversed: CI cannot reach a SQLite file living on Hostinger, which makes
  `payload migrate` unrunnable in the pipeline. Do not switch back.
- **English only.** No i18n now. But do not make choices that block a later
  document-level i18n retrofit (`@sanity/document-internationalization` equivalent for
  Payload is its built-in `localized` flag) — keep one document per content item.
- **No donations, no payments, no user accounts** beyond Payload admin auth.
- **Uploads to local disk**, not S3/R2. 50 GB and unlimited bandwidth make object
  storage unnecessary here.
- **Cloudflare free tier in front** for CDN and image caching. Nameservers currently
  `ns1/ns2.dns-parking.com` and will need to move.
- **Static generation for all public pages**, revalidated by webhook from Payload on
  publish. The database is touched at build time and in the admin panel only.
- **Artifact deployment.** GitHub Actions builds, Hostinger receives a tarball. The
  workflow already exists as `deploy.yml` — wire it up, don't rewrite the strategy.

## 5. Content model

Payload collections. Keep fields minimal — every optional field is one the NGO won't fill.

### `users`
Payload auth. Roles: `admin`, `editor`. Editors cannot delete collections or manage users.
Access control in code, not in the UI.

### `media` (upload collection)
- `alt` — **required.** No exceptions; enforce with validation.
- `credit` — optional text.
- Image sizes generated by `sharp`: `thumb` 400w, `card` 800w, `hero` 1800w. Enable
  focal point / crop so staff set the subject once and no ratio decapitates anyone.
- **Validation: reject images narrower than 1200px** for anything destined for a hero or
  card slot. Their photo library is inconsistent and this is the guardrail.
- `staticDir` must be an **absolute path outside the release tree** — see §8.

### `projects`
`title`, `slug`, `status` (`ongoing` | `completed`), `startYear`, `endYear`,
`locations` (array: district, municipality), `partners` (array of text),
`focusAreas` (relationship, hasMany), `summary` (textarea, max ~240 chars),
`body` (Lexical rich text), `gallery` (media, hasMany),
`relatedPublications` (relationship to `publications`, hasMany),
`outcomes` (array of `{ label, value, unit }` — feeds the tally section in §7).

This collection is what fixes the dead `#` links.

### `publications`
`title`, `slug`, `type` (`report` | `policy-brief` | `journal-article` | `sbcc-material`
| `annual-report`), `year`, `authors` (array), `abstract` (textarea),
`file` (upload, optional), `externalUrl` (optional, for DOIs),
`relatedProjects` (relationship, hasMany).

Validate that at least one of `file` or `externalUrl` is present.

### `focusAreas`
`title`, `slug`, `shortDescription`, `order`. Five of these, once SIDDHI decides.

### `team`
`name`, `role`, `category` (`board` | `staff` | `advisor`), `bio`, `photo`, `order`.

### `posts`
`title`, `slug`, `publishedAt`, `excerpt`, `coverImage`, `body`,
`author` (relationship to `team`).

### `partners`
`name`, `logo`, `url`, `type` (`funder` | `implementing` | `academic` | `government`).

### `pages`
Flexible block-based pages for About and Contact. Blocks: `richText`, `imageWithCaption`,
`statRow`, `teamGrid`, `contactBlock`. Resist adding more.

### Globals
- `siteSettings` — contact details, address, social links, SWC registration number,
  organisation registration details. These appear in the footer and are currently
  hardcoded on the old site.
- `homepage` — hero headline and standfirst, selected impact figures, chosen featured
  projects and publications. The landing page reads from here, not from hardcoded arrays.

## 6. Design direction

Read the brief below before writing CSS, and do a short design plan pass first. Avoid the
current AI-design defaults: cream background with high-contrast serif and terracotta
accent, near-black with an acid accent, and broadsheet hairline-rule layouts. An earlier
draft of this brief pointed at that third one; it's been deliberately replaced.

### The direction: field instrument

Ground the visual language in the artifacts of public health data collection in Nepal —
survey questionnaires, immunization cards, growth-monitoring charts, tally sheets,
district codes. Structured, gridded, data-forward, with labeled fields. This is
SIDDHI's actual working material, and it reads as rigorous rather than charitable.

Concretely: a faint graph-paper substrate; content sections that carry field labels and
codes the way a form does; figures set in monospace; annotation-style highlights over
printed structure.

### Tokens (placeholder — replace `--ink-accent` once SIDDHI confirms brand colour)

```
--paper:        #F2F4F5   /* cool pale grey-blue substrate, deliberately not cream */
--grid:         #DCE2E5   /* graph paper rule, very low contrast */
--ink:          #1B2A3A   /* primary text — slate, never pure black */
--ink-muted:    #5A6B7A
--ink-accent:   #0F6E5C   /* clinical green — placeholder */
--annotate:     #E8A33D   /* ochre, used only for the annotation layer */
```

### Type

- **Display:** Archivo — tight tracking, heavy weights, used with restraint.
- **Body:** Newsreader — a serif for long-form research prose, which is what this
  organisation actually produces.
- **Utility/data:** IBM Plex Mono — figures, district codes, field labels, captions.
  The monospace face is doing real work here; it encodes "this is data."

All three are on Google Fonts, and all three have paths to Devanagari support if Nepali
is added later. Self-host the subsets; don't hotlink.

### Handling inconsistent photography

Their photo library is mixed quality and this is the single biggest threat to the site
looking professional. The fix is systemic, not curatorial:

1. **Duotone treatment applied globally.** Grayscale the image, overlay `--ink-accent`
   with `mix-blend-mode: multiply`, add a subtle grain layer. A phone snapshot and a
   DSLR frame become visual siblings. Build this as one reusable component and never
   render a raw photo outside it.
2. **Never full-bleed a photo.** Constrain every image to a framed slot — resolution and
   noise problems only show at scale.
3. **Type carries the page, not images.** Where a photo would be weak, use the tally
   figures, the data, or set type large instead.

### Signature element

**Tally grids for impact figures.** Do not build odometer-style counting numbers — that
is the template answer and it obscures scale. Instead render each figure as a dot matrix
where one mark represents a fixed unit (say one dot per 50 people surveyed), filling in
on scroll. It comes directly from tally sheets, it makes magnitude legible rather than
merely impressive, and it is the one memorable thing on the page. Spend the boldness
here and keep everything around it quiet.

## 7. Landing page and animation

Stack: `gsap` with `ScrollTrigger` and `SplitText`, driven through `useGSAP()` from
`@gsap/react` for correct cleanup under React strict mode. `lenis` for smooth scroll,
wired into ScrollTrigger via `lenis.on('scroll', ScrollTrigger.update)` and
`gsap.ticker.add`. All GSAP plugins are free under the standard licence now.

Wrap **every** animation in `gsap.matchMedia()` with a `(prefers-reduced-motion: reduce)`
branch that renders final states immediately, and a mobile branch that drops pinning and
horizontal scroll entirely. This is a quality floor, not a nice-to-have — a meaningful
share of the audience is on mobile data in Nepal.

Sections in order:

1. **Hero** — typographic. `SplitText` line-by-line mask reveal on the mission
   statement. At most one duotone image in a constrained frame. No video background.
2. **Impact tally** — the signature element from §6. `ScrollTrigger` staggers dots
   filling in. Figures come from `homepage` global.
3. **Where we work** — **DO NOT BUILD YET.** Blocked on §4 question 1. An animated
   district map with three pins looks thinner than no map at all. If the real count is
   fifteen-plus districts, build it with `DrawSVG` on district outlines. If it's three,
   build a data visualisation from the climate survey instead.
4. **Focus areas** — pinned horizontal scroll, five panels, presented as numbered form
   sections with field labels. Purely typographic, so photo quality is irrelevant. This
   is the safest high-impact moment on the page.
5. **Featured research** — cards with `clip-path` reveals on staggered `ScrollTrigger`
   entry, linking to real project and publication pages.
6. **Partners and contact** — slow seamless marquee of partner logos, then static
   contact details from `siteSettings`.

## 8. Deployment

### `next.config`

```js
output: 'standalone',
outputFileTracingIncludes: {
  '/**': ['./node_modules/sharp/**/*', './node_modules/@img/**/*'],
},
```

The `@img` glob is required. Sharp 0.33+ moved platform binaries into separate optional
packages, and tracing `sharp/**` alone yields the wrapper without the binary — producing
`'sharp' is required to be installed in standalone mode` at runtime. If it still fails,
add `npm install --no-save sharp` inside `.next/standalone` as the final build step.

### Server layout — create this by hand before the first deploy

```
~/releases/<sha>/    immutable builds, last 5 retained
~/current            symlink; rollback = repoint this
~/data/media/        uploads, symlinked into each release
```

Payload's `staticDir` points at `~/data/media` by absolute path. **If uploads live inside
the release tree, every deploy silently deletes the NGO's entire photo library.** This is
the one mistake here that isn't recoverable.

### Environment variables

- `DATABASE_URI` — Neon connection string. GitHub secret **and** server env.
- `PAYLOAD_SECRET` — GitHub secret **and** server env.
- `NEXT_PUBLIC_SERVER_URL` — **build-time only.** `NEXT_PUBLIC_*` values are inlined
  during `next build`, so setting this on the server is a silent no-op.

### Native modules

`sharp` and the Postgres bindings ship prebuilt per platform and libc. `ubuntu-latest`
is x64 glibc and Hostinger's containers almost certainly match, so this should work — but
suspect it first if the app builds cleanly and then throws on boot.

### Request body size

The 4.5 MB limit that would have applied on Vercel serverless does not apply here. But
verify Hostinger's proxy doesn't cap upload size independently. If it does and you can't
change it, add client-side image resizing in a custom Payload upload component, because
staff will upload whatever their phone produced.

## 9. Build order

1. Payload config, collections, access control. Run `payload migrate` against Neon.
2. Seed script importing existing copy from the current site — mission, focus areas,
   the three known projects, team, contact details. Don't retype it by hand.
3. One vertical slice: `projects` collection → `/work/[slug]` detail page, statically
   generated, with webhook revalidation working. Prove the whole path before widening.
4. Remaining detail pages and index pages: publications, posts, team, about, contact.
5. Design system: tokens, type scale, duotone image component.
6. Landing page sections, unanimated. Confirm layout works with real content.
7. Animation, last. It's the part most likely to expand indefinitely and it should sit
   on top of something already working.
